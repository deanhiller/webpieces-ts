### ③ Worktree commands judged against the primary tree — 8 repos including `0.4.697`

L1 resolved `root=` to the primary clone for commands whose `cwd` is a linked worktree, so the
branch and stale-main verdicts describe a tree the agent is not standing in. Worst offender
`monorepo1` (0.4.697): **14 commands across 4 worktrees**, led by `agent-a35e54eba1838ca7b` (7) and
`agent-ad59b72b9cab13d4b` (5). Also in monorepo2/3/4, monorepo-nx1/2/3, webpieces-ts30/40/50.

This is a **correctness** finding, not a slowdown — it is the known L0/L1 resolution split, and it is
the one place where a stale-main or branch verdict could be computed against the wrong tree entirely.

### ④ Docs name a `build.log` that is not on disk — `0.4.697` (monorepo1, monorepo2)

Both repos' docs point at `.webpieces/build.log` and `.webpieces/build.log.bak`. Neither exists.
The only real logs are under `.webpieces/worktrees/<agent-id>/build.log`. An agent that greps the
documented path gets silence, which is indistinguishable from a clean build — and the recorded
failure mode is that it re-runs the build instead.

Highest-leverage fix on the list: it is a path string, and it is on the current release.

## 3. The guards are working — and the loudest signal is the AI, not the tooling

`stale-main-bash-guard` is the #1 blocking rule by 6.6×: **86 of 131** L2 blocks, 109 block markers
in transcripts, 22.2 min of blocked wall-time across 251 calls.

**This is not a cost finding, and the first draft of this report got that wrong.** A high block count
is only a finding when the same block repeats with no progress between. Here the blocks are the
guard doing precisely its job, and the interesting behaviour is on the agent's side. Classifying all
44 stale-main blocks in monorepo4 session `687387ac` (0.4.697, main 15 commits behind origin):

| what was blocked | n | verdict |
|---|---|---|
| read of **repo-tracked source** on stale main | 12 | **correct — a wrong answer was prevented** |
| the **cure bundled into the same call as the work** | 12 | **correct — see below** |
| scratchpad / skill-file reads (`/private/tmp/…`, `~/.claude/skills/…`) | 8 | over-broad |
| health checks, git metadata, worktree ops (`curl localhost`, `ps -p`, `git worktree list`) | 12 | over-broad |

**The 12 content reads are the case that justifies the whole guard.** One of them is
`sed -n '598,612p' eslint.config.mjs; echo "=== rule text ==="` — the agent was a step away from
quoting an eslint rule out of a file 15 commits stale and reasoning from it. Reading stale source and
believing it is current is a silently wrong answer, which is the expensive kind. Each of those 12
blocks bought a correct answer for the price of one round trip.

**The 12 compound blocks are the AI trying to outrun the guard, and they are the more telling half.**
The agent bundled a state-mutating fix with a state-dependent read in one shell call, and when that
was refused it tried again with a different spelling — **four distinct ones**:

```
pnpm wp-checkout-clean-main >/dev/null 2>&1; git log --oneline -1; … sed -n '598,612p' eslint.config.mjs
git fetch --prune origin main -q && git pull --ff-only origin main 2>&1 | tail -1 && sed -n '30,75p' …
git pull --ff-only origin main 2>&1 | tail -1; git log --oneline -3; …
git status --porcelain | head; … git fetch origin main -q && git rev-list --count HEAD..origin/main
```

Blocking these is right, and the first one shows why. `>/dev/null 2>&1` **silences the very command
the rest of the line depends on.** If that pull hits a conflict, a dirty tree or a network failure,
the agent sees nothing and the `sed` runs against still-stale content while the agent believes it is
fresh. The guard evaluates the whole call before any of it runs and cannot know the first segment
will succeed — so refusing the bundle is the only safe verdict. An agent that wants fresh content
runs the cure alone, reads the result, and *then* issues the work.

**And the cure itself works.** Tracing `localMain=` through that session gives a clean chain
(`21f2c312→5815dce2→ebbbdb42`, 15 distinct pairs): the agent pulled every time and local main
genuinely advanced. It re-blocked because origin/main had moved *again* — that session was itself
landing PRs into the repo it was reading. So 44 blocks is not 44 tooling failures. It is one agent
choosing to do exploratory reads on a fast-moving `main` instead of branching first, as CLAUDE.md
says to, and getting caught every time it mattered.

### The guard prescribes what CLAUDE.md forbids — and that explains the four spellings

Counting every `cure=` the rule emitted fleet-wide:

| cure text the agent was handed | times |
|---|---|
| `git pull origin main, or git checkout -b <new> origin/main` | 119 |
| `git checkout -b <new> origin/main` | 112 |
| `git checkout main && git pull origin main` | 1 |
| **`pnpm wp-checkout-clean-main`** | **6** |

**Four cure texts for one rule, and the sanctioned one appears in 6 of 238 prescriptions.** CLAUDE.md
names `pnpm wp-checkout-clean-main` as the one command for this intention and explicitly warns
against hand-rolling `git checkout main && git pull`, because that is the same command minus the
orphan-directory sweep. The guard prescribes the forbidden form 231 times out of 238.

That substantially revises the reading above. The agent's four spellings are less "working around a
refusal" than an agent caught between two authorities telling it different things and improvising a
hybrid of both. **This is a tooling defect, and it is the largest one in this section.**

Fixing it is also what makes the composition question small: `cure_bundled_and` is only **4 blocks**
fleet-wide and `cure_bundled_semicolon` **12**, so the round trips at stake are single digits once
agents are told the right command.

*Residual, and it is genuinely minor:* the over-broad blocks (scratchpad reads, health/metadata
commands) — `tail` of a file under `/private/tmp/…/tasks/` cannot be stale in any
sense the guard cares about. The guard already has a `not-a-content-read (cure/build/metadata)` allow
class and it fired correctly elsewhere in the same session (row 4, on `git status && git branch`);
widening it to cover paths outside the repo would remove them without touching either of the two
categories above. Worth doing, not worth prioritising over §2.

**Fleet totals, now that the collector classifies rather than counts** (`stale_main_health`):

| bucket | blocks | meaning |
|---|---|---|
| `prevented_stale_read` | 17 | guard earned its keep |
| `cure_bundled_semicolon` | 12 | agent's defect — `;` runs the work even if the pull failed |
| `cure_bundled_and` | **4** | **tooling defect** — `&&` already short-circuits; blocking buys nothing |
| `blocked_badly` | **5** | **tooling defect** — target is outside the repo |
| unclassified | 46 | git metadata, health checks, mixed shapes |

**`blocks_that_bought_nothing` = 9** across the whole fleet for three days. That is the honest cost
of this rule, against 17 wrong answers prevented.

Two sessions came back **`cure-not-taking`** — the same `(localMain, originMain)` pair repeating with
no advance, which is the one shape here that is a real deadlock: `monorepo3` `badb2448` (10 blocks,
5 repeats) and `monorepo-nx1` `cd436790` (6 blocks, 2 repeats). Everything else verdicted `healthy`:
the blocks moved the tree forward and origin moved again.

## 7. Fixes made to the audit tooling itself

Three bugs in `/audit-webpieces`, all found by running it:

1. **`MATRIX_FILES` had no `L1` entry.** A layer missing from that dict is indistinguishable from a
   layer with no matrix, so the audit reported *"L1 emits row numbers no matrix defines"* as MAJOR on
   **five repos at once** — 650 citations in monorepo3 alone. `webpieces.location-matrix.md` exists in
   every one of them. Adding L1 collapsed 5 MAJORs to 5 cosmetic cure-text MINORs and left exactly one
   real finding (webpieces-ts50, above). It was reporting the opposite of the truth.
2. **`AskUserQuestion` counted as a failed tool call.** One 109-minute prompt waiting on a human was
   43% of the fleet's entire "failed call" time (8,671s → 3,815s once excluded) and would have been
   this report's headline. Human latency is not AI waste.
3. **No `--until`, so a closed window could not close.** A "Mon–Wed" audit silently ran to *now* and
   swallowed Thursday. Both collectors now take `--since`/`--until` as absolute UTC.

4. **The collector counts blocks; it does not classify them** — and counting alone produced the
   wrong headline. The first draft of this report led with stale-main as a *tooling defect*, on a
   block count and one quoted log line. Classifying all 44 blocks in the session (§3) inverted it:
   24 of them are the guard correctly refusing a wrong answer or refusing the AI's attempt to smuggle
   one past it. `digest.py` should split `blocks_by_rule` into *prevented-a-wrong-answer* /
   *agent-retried-a-refused-shape* / *over-broad* before any block count is allowed to be a finding.
   SKILL.md already said to make that distinction; nothing enforced it.

Plus the two things you asked for: `by_version` in the ledger (per-release builds/minutes/fails/
kills, `latest_in_window`, `pct_on_latest`), a version header in the digest, and a rule in SKILL.md
that every finding names the release it was measured on and the latest gets the weight. SKILL.md also
pointed `$SK` at `~/.claude/skills/audit-webpieces/scripts`, which does not exist — the skill lives
in the repo.
