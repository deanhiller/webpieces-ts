## 1. MAJOR — a stage-everything amend in a shared tree swallowed an unrelated agent's file, twice

**Found the hard way: this report was swept into another agent's commit and then deleted, 36 minutes
after it was written.**

Two sessions were working the SAME checkout. This report was written untracked at 09:52. Between
09:55 and 09:57 the other session amended its commit four times, and the report was byte-for-byte
inside two of those amends:

| time | commit | this report inside it? | files in the commit |
|---|---|---|---|
| 09:55:43 | `00874fa4` | **YES — 9,775 bytes** | 6 |
| 09:56:12 | `d0446e61` | removed | 5 |
| 09:57:29 | `4a855fc9` | **YES — 9,775 bytes** | 6 |
| 09:57:42 | `e64d62a5` | removed (final) | 5 |

The commit is titled *"Squash merge of dean/design-html-no-inline-style (conflicts resolved)"* and its
other five files are all on-topic for that branch. The audit report had nothing to do with it. The
only way an untracked file lands in an unrelated commit is a **stage-everything** step —
`git add -A` / `git commit --amend -a` — and backing it out again is what removed it from the working
tree. Nothing was archived to `.webpieces/trash/`.

**The deletion is the second-worst outcome here.** The worst is that it nearly *shipped*: had either
`00874fa4` or `4a855fc9` been the version that landed, a fleet audit naming client repos would have
been published inside a PR about inline-style CSS. A stage-everything commit in a shared tree does not
just destroy other agents' work — it can publish it.

**Note the earlier draft of this finding blamed `wp-review-upsert-pr`'s tree reset.** That was wrong:
the gate ran at 10:05, *after* the file was already gone at 09:57. The reflog and the blob contents
are what settle it. Timing correlation is not mechanism.

**Direction:**

- An agent working a tree it may share must stage **explicit paths** — `git add <path>` — never
  `git add -A`, `git add .` or `commit -am`. This is the whole fix and it costs nothing.
- The gate could refuse to amend when the staged set contains files outside the branch's own diff, and
  say which — the same instinct `wp-cleanup` already applies to branches, where every removal is
  logged with a pre-delete SHA and a `recover=` command.
- Untracked files swept out of a commit should land in `.webpieces/trash/`, not nowhere.

## 2. MAJOR — the stale-main guard is RIGHT; the cost is the agent substituting its own cure

**Cost:** 31 of 41 blocked decisions fleet-wide (76%), all `stale-main-bash-guard`. One session
(monorepo-nx2 `1b6453bd`) took **~7 minutes and 19 blocks** to comply.

**The guard is doing exactly what it should, and it is the most valuable thing in this audit.**
Reading a `main` that is tens of commits stale produces confidently wrong work — wrong file contents,
wrong APIs, wrong conclusions — and every token spent after that read is spent on a false premise.
That failure is orders of magnitude more expensive than any number of instant denials. **Do not
loosen this guard.** An earlier draft of this report suggested allowing read-only commands through on
`main`; that recommendation was wrong and is withdrawn.

**What actually cost the time** — the timeline says it precisely:

| time | event |
|---|---|
| 04:08:47 | session's first tool call |
| 04:08:48 | first block, cure printed: `git checkout -b <new> origin/main` |
| 04:09:18 | agent runs **`pnpm wp-checkout-clean-main`** instead — ALLOWED |
| 04:09:18 → 04:09:43 | blocks continue (`ls`, `find`, `git grep`, `grep -rn`) |
| **04:15:35** | agent finally runs `git checkout -b dean/whatsapp-api-authoidc origin/main` |

The guard printed the correct cure on the **first** block. The agent substituted a plausible neighbour:
`wp-checkout-clean-main`, which fetches and pulls `main` — and leaves you **standing on `main`**, which
is itself the blocked state (L2 row 5: on `main` → block, for bash). So the agent "fixed" staleness and
stayed blocked, then spent six more minutes discovering that.

**Direction — how to get the AI updating, without weakening the block:**

- **`wp-checkout-clean-main` should end by branching**, or refuse when an agent runs it, because
  standing on `main` is a state the guards block by design. Today the tool's success state is a
  blocked state. That single change converts the wrong-but-plausible cure into the right one.
- Fire the requirement **once at session start** when `main` is stale, rather than on the Nth command
  — the agent then branches before its first read instead of after its nineteenth.
- The block message could name why the neighbour fails: "`wp-checkout-clean-main` leaves you on `main`
  and you will be blocked again — branch instead."

**What the guard prevented, measured:** 31 reads of a stale tree that never happened.

## 3. MAJOR — the build.log path fix has NOT propagated to the ctoteachings consumer repos

**Correction to an earlier draft of this report, and a lesson about this audit's own method.**

`webpieces-ts` `origin/main` **already fixes this**, and with a better rule than the one this report
first proposed:

> **Read the log at the absolute `FullLog :` path THIS run printed — never type a path from memory.**
> … from a linked worktree — the normal case for a subagent — it is
> `<primary>/.webpieces/worktrees/<worktree-name>/build.log`, and a relative `.webpieces/build.log` in
> the worktree does not exist at all.

The first draft flagged webpieces-ts30/40/50 anyway, because the collector read **working-tree** docs
and those checkouts are 3, 5 and 3 commits behind `origin/main`. That is this audit committing the
exact failure finding 2 exists to prevent: **reasoning off a stale main.** The collector now reads
tracked docs from `origin/main` and reports each repo's behind-count; webpieces-ts30 and monorepo-nx2
correctly drop off the list.

**What survives the correction is real, and it is a propagation gap.** These consumer repos still name
the bare path in their own `origin/main` — not a stale checkout, the actual main branch:

| repo | behind origin/main | CLAUDE.md on ITS origin/main |
|---|---|---|
| ctoteachings/monorepo2 | **0 — fully current** | still names `.webpieces/build.log`, no worktree awareness |
| ctoteachings/monorepo1 | 4 | same |
| ctoteachings/monorepo4 | 1 | same |

monorepo2 is the proof: it is not behind anything, and its CLAUDE.md still sends an agent building in a
worktree to a path that does not exist there — while its real logs sit in
`.webpieces/worktrees/agent-ad233d02490ed8716/build.log`.

**Direction:** the corrected "read the printed `FullLog :` path" wording needs to reach the consumer
repos' own CLAUDE.md. Note `.webpieces/worktrees/<agent>/` is not a git worktree and never appears in
`git worktree list`.

## Caveats on method

- Guard-log counts are **deduplicated**: one call is logged twice (coordinator log + per-call log), so
  raw row counts overstate by ~2×. The 41 figure is deduped; a naive count says 75.
- Transcript-side block detection (146) is an **upper bound** and does not equal the guard-log figure
  (41): it matches denial text at the head of a tool result, which also catches subagent-relayed
  denials. **Trust the 41.**
- The guard logs do **not** record the wp-* tooling's own git operations, nor another session's git
  commands. Finding 1 was invisible to them and was reconstructed from `git reflog --date=iso` plus
  `git show <sha>:<path>` on each amended commit. The first draft of that finding blamed the wrong
  mechanism from timing alone — read the blobs.
- `active time` excludes gaps >5 min, so it is attention time, not wall time; parallel agents are not
  separated, so treat totals as cost ordering rather than a timesheet.
- **Docs are read from `origin/main`, not the working tree** (fixed mid-audit). The first draft
  reported build.log drift in webpieces-ts30/40/50 that main had already fixed, because those
  checkouts are 3-5 commits behind. Any doc finding from an earlier run should be re-checked against
  `origin/main` before being believed. A path a doc names in order to say it is NOT there is also no
  longer counted as drift.
- A 4.6h window is small. Items 1, 3, 5, 7 and 8 are structural (true regardless of window); items 2
  and 6 are rate-based and worth re-measuring over 7 days.
