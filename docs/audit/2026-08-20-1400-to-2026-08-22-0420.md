## 1. MAJOR — the 600s foreground watchdog fired 10 times, and `wp-review-upsert-pr` is one of the things firing it

**Cost: ≥100 minutes of wall time reaching the cap, plus the polling round-trips after each one.**
This is the single most expensive measured pattern in the window, and it is a *harness* cost, not a
guard cost.

The Bash tool moves a foreground command to the background after 600s. Ten commands hit that in
38 hours, across eight distinct agents:

| when (UTC) | agent / session | the command that stalled |
|---|---|---|
| 08-20 11:22 | `agent-a16e3faec3ec3d1f2` | (not recoverable — rotated) |
| 08-20 12:16 | `agent-a74181c8b7d2107e1` | `gh run list --limit 20 --json …` |
| **08-20 12:32** | `agent-aae63ef3aebde451f` | **`pnpm wp-review-upsert-pr 2>&1 \| tail -35`** |
| 08-20 12:42 | `agent-aae63ef3aebde451f` | `until grep -q "STEP 3\|Build Failed\|❌" …` (a poll loop) |
| 08-20 13:04 | `agent-a7e3a15b6e860dc73` | a `find ~/.claude/projects … \| while read f` transcript sweep |
| 08-20 13:18 | `agent-a7e3a15b6e860dc73` | `gh run watch 32372524510 --exit-status` |
| 08-20 17:06 | monorepo1 `59a270bf` | (not recoverable) |
| 08-20 17:51 | `agent-a6edeff680e6e82cb` | a scratchpad `wa…` wait script |
| 08-21 05:54 | `agent-a547944a392c11135` | `gh pr checks 1015 --watch` |
| 08-21 07:17 | `agent-afae322fb92d7ec5f` | (not recoverable) |

Three shapes account for all of it, and they want three different fixes:

- **Stage ② run in the foreground.** `pnpm wp-review-upsert-pr` legitimately takes longer than 600s
  — it validates the merge and *runs the build*. Piping it to `tail -35` guarantees the agent sees
  nothing until it finishes, so the watchdog fires on the one command in the workflow that is
  *supposed* to be slow. The agent then discovers this the expensive way.
- **`gh run watch` / `gh pr checks --watch`.** Blocking CI waits, three of ten fires. They are
  designed to sit silent for minutes; the harness is designed to kill things that sit silent for
  minutes.
- **An agent's own `until grep …` poll loop** — written to *work around* backgrounding, and then
  itself backgrounded.

**Why it costs more than the 10 minutes each.** Backgrounding is not free recovery: the agent then
burns a call per poll, and — as this very session did after being killed and restarted — may not
know whether the work completed at all. One of the two unrecoverable fires belongs to an agent
whose next act was to re-run its build.

**Direction:**
- `wp-review-upsert-pr` should either stream progress lines unbuffered (a heartbeat, the way
  `wp-build` already prints `… size 100 lines` / `still`) or be documented as
  **run-it-with-an-explicit-timeout**. It is the tooling's own longest command and the one most
  likely to be piped to `tail`.
- The workflow doc should say plainly: give stage ② and any `gh *watch* ` an explicit
  `timeout: 600000`, and never pipe stage ② through `tail` — that is what removes the heartbeat.
- The `until grep` poll loop is a symptom worth reading: agents are hand-rolling a wait primitive
  because the sanctioned one is not obvious.

## 2. MAJOR — the new build ledger's first catch: 9.4 minutes of build for one result

**This finding did not exist before 2026-08-21.** It is only visible because
`~/.webpieces/builds.log` shipped in @webpieces 0.4.687 — and it is exactly the class the ledger was
built to make visible.

```
START        06:51:02Z  by=review  repo=…/webpieces-ts40  tree=agent-afc542b5b472408b0
DONE-FAIL    06:56:43Z  took=340998  exit=130
START        07:00:21Z  by=review  repo=…/webpieces-ts40  tree=agent-afc542b5b472408b0
DONE-SUCCESS 07:04:05Z  took=224253
```

`exit=130` is **128+SIGINT** — the build was *killed*, not failed. A red build has answered its
question; a killed build has answered nothing, so its entire 5.7 minutes is burned. The agent
re-ran the identical stage ② 3.6 minutes later and got a green in 3.7 minutes. **9.4 minutes of
build for one usable result, 61% of it waste.**

The ledger records the effect, not the cause: nothing in it says *who* sent the SIGINT. It was not
the 600s watchdog — 340,998 ms is well under the cap, and no watchdog fire is logged for that agent
at that time. A cancelled agent, a closed terminal, or a supervisor kill all fit.

**The same worktree ran stage ② a third time 18 hours later** (08-22 01:04Z, 4.7 min, green).
`agent-afc542b5b472408b0` alone accounts for **14.1 of the window's 19.4 ledger-recorded build
minutes** — 73% of every build minute this box logged, in one worktree.

**Direction:** the ledger already has everything needed to *say so at the time*. A stage that finds
its own previous START on the same repo+tree with no DONE, or with a signal exit, could open with
"the last build in this tree was killed after 5.7 min and never re-verified" instead of leaving the
agent to rediscover it. Recording the fact is step one; surfacing it is what converts it to saved
time.

## 3. MAJOR — 43 rule hatches fleet-wide are pinned to branches that do not exist

Every repo carries `turnOffRuleWhileOnBranch` escape hatches. **Not one of the four branches they
name still exists — locally or on `origin`:**

| repos | branch named by the hatch | rules held open | exists? |
|---|---|---|---|
| monorepo-nx1, nx2, nx3, nx4 | `dean/one-2595-partner-apis-move` | `require-return-type`, `no-inline-type-literals`, `no-any-unknown`, `no-destructure`, `no-symbol-di-tokens` | **no / no** |
| ctoteachings monorepo1-4 | `rename-fuse-to-theme` | `max-method-lines`, `no-any-unknown`, `no-destructure`, `no-custom-css`, `no-function-outside-class` | **no / no** |
| webpieces-ts30, ts40, ts50 | `dean/bump-webpieces-0-4-658` | `no-any-unknown` | **no / no** |

43 entries. All dead.

**Why this is MAJOR rather than tidy-up.** The hatch is *supposed* to be the loud, greppable,
self-expiring form of "this rule is off" — the alternative to a silent widening, per CLAUDE.md's
shim shape #5. A hatch naming a deleted branch inverts that: it reads to a human (and to an agent
grepping the config) as an active, deliberate exemption with a live justification, when in fact the
rule is on for everyone and has been for weeks. Every one of these is a question an agent may stop
to reason about and a reviewer may accept as intentional.

The webpieces-ts hatch is dead **twice over**: its `turnOffRuleUntilEpoch` is `1783409251` =
**2026-07-07**, expired 46 days ago, alongside a branch that is gone. Nothing about it can ever fire
again.

**Direction:** an expired hatch is exactly the shape `wp-prune-unknown-config` already handles for
unknown keys — a mechanical, provably-safe deletion. A `turnOffRuleWhileOnBranch` naming a branch
absent from both local and `origin`, or a `turnOffRuleUntilEpoch` in the past, is dead by
construction and could be reported (or reaped) by the config validator that already reads the file
on every startup. Note the fleet's *other* expired epoch, `1771931925` = 2026-02-24, appears on ~12
more rules; those are harmless but they are the same litter.

## Caveats on method

- **The ledger covers 19.3 of 38.3 hours.** Findings 1, 3, 4, 6, 7, 8 and 9 are structural and hold
  for the whole window. Finding 2 and every number in finding 5 describe the covered half only.
- **Watchdog fires are counted from tool RESULTS, not from any line containing the phrase.** The
  first pass counted 14; four were this audit's own `grep "600s timeout"` commands appearing in its
  own transcript. Three of the ten survivors' commands could not be recovered because the preceding
  tool call had rotated out. Treat 10 as a floor.
- **A collector bug was fixed mid-audit and it mattered.** `audit_docdrift` did not expand `~`, so
  it reported `~/.webpieces/builds.log` — the new machine-global ledger, named by every repo's
  `webpieces.buildlog.md` — as a doc naming a nonexistent path, in every repo. That is the second
  window running in which this skill's first draft manufactured a doc-drift finding out of its own
  resolution rules. Fixed in `wp_audit.py`; any `~`-rooted drift finding from an earlier run is
  void.
- Guard-log counts are **deduplicated** (each call is logged twice, coordinator + per-call). The 82
  figure is deduped.
- Transcript-side block detection (191) is an **upper bound** and does not equal the guard-log
  figure (82): it matches denial text at the head of a tool result, which also catches
  subagent-relayed denials. **Trust the 82.**
- Docs are read from **`origin/main`**, not the working tree, per the correction in the last report.
- `active time` excludes gaps >5 min, so it is attention time, not wall time; parallel agents are
  not separated, so treat totals as cost ordering rather than a timesheet.
- **This audit was itself killed mid-run** (spend limit) and resumed against a verified tree. That
  is not a data point about the fleet, but it is the same failure class as finding 2: a long job
  whose progress was recoverable only because something on disk recorded it.
