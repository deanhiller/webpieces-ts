# Responsibilities — docs-site

Render a static, three-pane API reference site from **any** conforming OpenAPI 3.0-or-3.1 document plus a directory of markdown prose, and ship the `wp-docs-site` bin.

**Node builtins only.** No framework, no markdown library, no bundler — so adding an API reference to an upstream project never grows that project's dependency surface, and this package's own build stays `tsc`.

## In Scope

- **One PRE-RENDERED HTML file per URL** — `index.html`, `prose/<slug>/index.html`, `reference/<kebab-operation>/index.html`, `schemas/<kebab-name>/index.html`. Deep links resolve server-side, the output is a folder any static host serves, JS off still reads, and a JSDoc edit shows up as a diff on the one page it affects
- The three panes: the collapsible nav tree, the operation body, and the sticky card column (authorization, code samples, `REQUEST` / `COLLAPSE ALL`)
- The parameter tree: field name, type label, prose, and for an enum the COMPLETE `Possible values:` chip line — all read from the spec
- `docs.manifest.json` names the markdown prose pages and their order
- Code samples built FROM THE SPEC — server url, path, security-scheme header names, a generated example body — in Go, raw HTTP, Java and JavaScript
- **Every OpenAPI tag is its own nav section**, in the document's own `tags[]` order
- **Webhooks** file into the SAME section as the operations sharing their tag, appended after them, badged, with no method, no path and no code samples
- A `oneOf` request body renders as one labelled variant per branch, keyed by the discriminator value, **all expanded** rather than tabbed
- **One page per named object DTO**, with every reference to it rendered as a LINK, while the generated EXAMPLE body stays fully resolved
- `$ref` expansion that is cycle-safe INCLUDING the root
- `DevServer` — a localhost-only static preview of the generated directory, via `wp-docs-site --serve`

## Out of Scope

- **Generating the document.** That is `@webpieces/openapi-generator`, and the section below says why this package does not even import it
- **Hosting.** `DevServer` is preview only: not hardened, not authenticated, bound to `127.0.0.1`
- A full CommonMark implementation — a documented subset over trusted, PR-reviewed input
- **Swagger 2.0.** It is a different document — schemas under `definitions`, no `webhooks` block — so reading one with this reader finds none of those keys and SUCCEEDS, writing a site with every field missing. `SpecLoader` refuses it by name and names the conversion instead: a wrong site is worse than no site, because only one of the two sends somebody looking for the bug
- Search, versioned docs, interactive "try it" consoles
- Vendor logos as language marks. The real gopher and Java cup are other companies' trademarks; the languages are labelled in words
- **Any nx API, repo path or app-specific type.** It imports nothing at all outside `node:` builtins

## Why it does NOT import `@webpieces/openapi-generator`

The generator's document classes are structurally identical to what this package reads, and importing them would save a few hundred lines. It is still the wrong call: a compile-time dependency would make **"generated by us" a precondition for "renderable by us"**, and the whole claim of this package is that it renders any conforming document — including one generated by `openapi-generator` from a *different release*, or by a tool that is not ours at all.

So the document is read STRUCTURALLY (`JsonNode`): every accessor asks "is there a string at this key", never "is this an instance of our class". `ForeignDocument.spec.ts` renders a 3.0 document written in 3.0's dialect, with a self-referential DTO, an undefined `$ref` and an untagged operation, precisely so the decoupling is a tested property rather than a stated intention.

## A reference arrives in THREE shapes, and reading only `$ref` drops two

| shape | written by |
|---|---|
| `{ "$ref": "…", "description": "…" }` | OpenAPI 3.1, where prose beside a `$ref` is legal |
| `{ "anyOf": [{ "$ref": "…" }, { "type": "null" }] }` | 3.1's nullable reference |
| `{ "allOf": [{ "$ref": "…" }], "description": "…" }` | 3.0, whose `$ref` siblings are ignored |

Reading only the first drops a field's whole type on any 3.0 document, and the field then renders with no type at all — which a partner reads as "they forgot to document it" rather than as a renderer bug.

A nullable field's type column shows the NON-null type, and `format` renders inside angle brackets: `string<date-time>`.

## Two trees on purpose: LINKS in the parameter tree, full resolution in the example

Every reference to a named OBJECT renders as a link to that object's page, and its fields are not inlined underneath. The generated example body resolves the same reference fully.

Sharing one tree is the tempting simplification and it is wrong in both directions. A hyperlink cannot live inside a JSON sample, so a shared tree that links prints `"data": {}` on a partner's page; a shared tree that inlines gives every DTO as many copies as it has use sites, and none of them is the page a reader can link to.

Only OBJECTS get pages. A named enum or scalar alias stays inline with its chips — a page holding one line of values costs the reader the context they were reading. An UNDEFINED `$ref` also stays inline: a link to a page the document never defined is a dead link, strictly worse than the unresolved type name it replaced.

**Cycle safety includes the ROOT.** A schema is marked seen BEFORE its own properties are read. Mark it afterwards and `Category { parent: Category }` recurses until the stack dies — a crash with no pointer in it rather than a page.

## Why a `oneOf` is expanded and never tabbed

A partner writing one handler needs every branch's shape at once. A tab is also invisible to Ctrl-F and to print, so the shapes behind the unselected tabs are, for a reader searching the page, simply not documented.

## Why every tag is its own section

A tag missing from the sidebar is an operation a partner cannot find, which reads exactly like an operation that does not exist. So the sections come from the tags themselves — including a tag only an operation mentions, and including an untagged operation, which gets an `Operations` section rather than vanishing.

## Two ordered sources, neither sorted

The reference order is the document's own `tags[]`; the prose order is `docs.manifest.json`'s `pages[]`. Both are published decisions somebody made. Alphabetising either is not a cleanup — it reorders partner-facing navigation.

## Why the links are RELATIVE and end in `index.html`

Root-relative links only work when the site is the whole host, and a generated reference is routinely served under a path (GitHub Pages does it by default), where every page but the home one would 404. So each page computes a `../` prefix from its own depth. Each href ends in `index.html` rather than a bare directory for the same reason: a directory URL needs a server willing to serve the index, and `file://` is not one.

## `DevServer` is a preview and not a host

It binds `127.0.0.1` and nothing else. No logging, no rate limiting, no TLS, no access control, and nothing here should be read as a claim that adding an address would make it safe to expose. The one security property it does enforce is that a request cannot escape the output directory — which is not hardening, it is the minimum for a process that opens a socket at all.

## The error type, and why it is not `RuleFailError`

Everything throws `DocsSiteError` to the single top-level handler in `WpDocsSiteMain`, which is the only renderer of a failure and the only writer of an exit code (`.claude/review/error-output.md`). `location` and `cure` are carried as FIELDS so the CLI renders them per audience.

`RuleFailError` lives in `@webpieces/rules-config` — the TOOLING stream, which a repo pins one release behind on purpose — while `packages/docs/*` publish with the SERVER libs. Depending across the two streams to reuse an error class would couple this package's release to the rule engine's. It is not `OpenApiGenerationError` either, for the decoupling reason above.

## Notes

Tagged `framework:node` and `role:lib`. It is in `scripts/publish-packages.sh`'s ORDER; like `api-doc-model`, `openapi-generator`, `core-mock` and `mcp-server` before it, the npm NAME has to be bootstrapped once by an authenticated manual publish, because trusted publishing can publish to an existing scoped name but cannot create one.

The bin is declared in `publishConfig.bin` and never at the top level (`.claude/rules/packaging-and-bins.md`).

`apps/app-example/partner-api` is the worked example: its `docs/` directory holds the prose and its manifest, and `docs-site-golden.spec.ts` renders the committed `public-openapi.json` and asserts the properties above.
