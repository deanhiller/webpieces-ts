# Responsibilities — pr-gate

Standalone CLIs for the gated PR workflow — start/finish-upsert-pr, start/finish-update (update from main), merge start/end — plus the red/yellow/green PR dashboard that computes merge-gate results and counts newly added rule disables.

## In Scope

- Bin commands shipped from `src/scripts/*`: `wp-start-upsert-pr`, `wp-finish-upsert-pr`, `wp-start-update` (update from main; clean → finalizes, conflict → hand off), `wp-finish-update` (finalize after resolving conflicts). The full-update composition (`runUpdateFromMain`) and 3-point merge-info gathering (`gatherInfo`) are internal `workflow/` functions, not bins.
- `wp-build` — the ONE way anybody verifies a change. It runs `commands.pr-gate.buildCommand` VERBATIM through `BuildAffected.runBuildGate`, the same shared gate stage ② and stage ③ use, so it inherits one resolver (`resolveBuildCommand`), one announce line, one capture path (`BuildGateLog`) and one failure rendering — only its `BuildGateOptions` differ, by `BUILD_STAGE`, which selects the fixed `.webpieces/logs/build.log` rather than the PR flow's per-commit files beside it. Its console contract IS the pointer at that file: the build's stdout+stderr are redirected there in full, the FIRST stdout line is `FullLog : <absolute path>` (printed before any work, so a backgrounded run still knows where to read — issue #1393), the console then gets a heartbeat every 10s and then `Build success` / `Build Failed:` plus the same `FullLog :` path, and every run first rotates the previous log to `build.log.bak` so the last TWO builds are on disk. That exists because an agent that could only read the console re-ran the whole build to see a different slice of it — 23.9 minutes across nine runs in one measured session, five with no code change between them. It composes nothing else on purpose: a per-repo verify chain is what drifted into building the world three times per inner loop, and anything that must run on every build belongs inside `buildCommand` where the gate runs it too. `whole-repo-build-guard` (ai-hook-rules) names this bin in its refusal.
- `wp-build-dev` — `wp-push-dev`'s pre-publish check without the publish (#1397): merges `origin/<devBranch>` into the throwaway `<branch>DevCheck`, runs `commands.push-dev.buildCommand` through the same `BuildAffected` gate (`DevBuild`, `DEV_BUILD_STAGE`, fixed `.webpieces/logs/build-dev.log`), and returns to the feature branch whatever happens. It resolves nothing — a conflict aborts the throwaway merge and names the files and `wp-push-dev`. The key has no default: `DevBuild.command` refuses, naming the key and printing the entry, before any git write.
- `wp-push-dev` (plain publish) — the same check, then the publish (#1397): `DevResolveRunner` in `DevResolveMode.PREBUILD` merges `origin/<devBranch>` into the throwaway, halts on a conflict for `wp-finish-push-dev`, runs the dev build, then `recordResolution` moves the throwaway back to the feature head and adds ONE commit holding only the resolved files. The merge is never published, so no other copy becomes an ancestor of this one. `--resolve` (`COMPOSE`) publishes the same way on top of the existing copy; `--rebase-resolution` (`REPLAY`) still publishes its merge.
- `wp-upsert-hotfix-pr` — the ONE command for a `/hotfix/` branch (issue #1057). A hotfix branch is cut from the production sha, so it must never take main: the command refuses a non-`/hotfix/` branch, requires a clean tree and `summary.json`, runs only `hotfix-ci`, never merges main or rewrites the branch, pushes once fast-forward only (`HotfixPrPublisher`), upserts the audit-bannered PR, and never enables auto-merge. On a `/hotfix/` branch the three PR stages refuse up front via `HotfixRedirect` and name it.
- The 3-point squash-merge / merge-validation gate workflow (`src/scripts/workflow`).
- The red/yellow/green PR dashboard (`src/dashboard/dashboard.ts`): `computeGateResults`, `countAddedDisables`, and its `GateResult`/`DisableCounts`/`DashboardInput` data classes. THREE renderings, one per surface: `renderPrBody` (the PR description, which is byte-identical to the squash-merge commit body — see `pr-body-is-merge-body.spec.ts`), `renderDetailComment` (the 1st PR comment: full dashboard, all rows, hash points), and `ChecklistCommentRenderer.render` in its own file (the 2nd comment: per-reviewer output). Both comments are upserted by hidden marker via `PrCommentUpserter`. `SquashSettingsEnforcer` keeps GitHub's `squash_merge_commit_title`/`squash_merge_commit_message` pinned to `PR_TITLE`/`PR_BODY` so a UI merge copies the description into `git log` — server-side settings no config key can express, repaired on every stage ③ run.

- Build-gate log capture (`BuildGateLog`) — ONE implementation, ONE durable file, every caller. `wp-build`, stage ② and stage ③ all redirect the build's full stdout+stderr to a file and hand back a `FullLog :` pointer; stage ② and stage ③ use `.webpieces/logs/build-gate-<stage>-<branch>-<shortSha>.log`, and the gate prints its `FullLog :` line before the build starts (per-commit, because review and finish can both run against ONE commit). It was briefly selectable, behind `experimental.buildGateLogCapture` in the machine-local `~/.webpieces/config.json` — a file essentially nobody has, so essentially every gate build streamed to the terminal and every failure said "run this command again yourself". Both halves of that were the defect, and the key is deleted rather than defaulted: an accepted shape is never migrated. AI-facing calls never stream or `tee`; only a human who answers Y inside `wp-human-post-pr` follows that same file live until completion.

- Stage console capture (`StageOutputLog`) — the same treatment for what the STAGES themselves print. `wp-review-upsert-pr` and `wp-finish-upsert-pr` run their body with stdout intercepted into `.webpieces/logs/wp-<command>.log`, and only what the caller must act on immediately is `say`-ed through to the terminal: the build heartbeat and result, stage ②'s reviewer/`summary.json` instruction block, and stage ③'s PR link and follow-ups. That exists because agents pipe these commands to bound them, a pipe withholds every byte until the command exits, and the harness kills a command silent for 600 seconds — after a full build. `build-output-pipe-guard` (ai-hook-rules) refuses the pipe; this is what makes refusing it reasonable. Each stage's FIRST stdout line is `FullLog : <its console log>`, before any work. `GateLogFile` is the one place that knows WHERE any of these logs go — `<tree>/.webpieces/logs/` through `DotWebpieces.aiFacing()`, i.e. inside the checkout the command ran in, a linked worktree's own root included, because an agent confined to its worktree may be refused a read anywhere else (issue #1393) — and keeps exactly one previous generation as `.bak`.

- Incomplete reviewer-round recovery (issue #1087): sanctioned main updates and squash rewrites do not consume a review round. Stage ② continues the original fixed roster against its original materialized diff and briefing SHA, and prints the remaining required checklist instructions. Accepted GREEN/YELLOW verdicts keep their historical provenance; only the existing RED follow-up policy starts another round, and the final-round ORANGE policy remains author remediation without re-review. The receipt's `buildHeadSha` tracks current build evidence independently of the historical `headSha`. Stage failure logs include the normalized terminal failure before capture closes.

## Out of Scope

- The actual code-quality gates being counted/rendered — implemented as ESLint rules in `eslint-rules` and Nx `validate-*` executors in `nx-webpieces-rules`.
- Architecture/DI/runtime graph generation — owned by `nx-webpieces-rules`.
- Rule mode/disable config schema — owned by `@webpieces/rules-config`; the dashboard only tallies disables it reads.

## Notes (optional)

Deliberately standalone — no Nx dependency required — so the PR/merge scripts run in CI and locally on their own. Published to npm via the release workflow (OIDC trusted publishing); the public library surface is intentionally small (dashboard gate computation) and mostly backs the bin commands.
